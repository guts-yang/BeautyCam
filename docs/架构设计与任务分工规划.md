# BeautyCam 架构设计与任务分工规划

> 依据：当前 `README.md`、`docs/设计方案-人脸美颜.md`、`src/prepare_data.py` 与 `data/input/README.md`。本方案面向现有三人团队 A/B/C；估算按 1 人日约 6–8 小时、具备 Python/OpenCV 基础计算，不含 CelebAMask-HQ 下载、报告之外的课程事务。

## 1. 结论与现状

建议采用轻量分层流水线，而非引入 Web/MVC 或服务化架构。技术栈保持 Python + OpenCV + NumPy，全部使用传统图像处理方法，不使用深度学习。

当前仓库已有数据预处理脚本与设计方案，但 `src/` 目前仅有 `prepare_data.py`；主流程、`beauty` 算法包、配置文件和测试尚未落地。因此下列分工是开发计划，不代表功能已实现。

## 2. 技术架构

### 2.1 分层结构

1. **入口与配置层**：`main.py` 提供单图/目录批处理命令；加载 `config.yaml`，校验路径、扩展名和算法参数。入口不包含算法实现。
2. **流水线编排层**：按配置调度阶段、管理图像与预测掩码状态、保存阶段结果；逐张图片隔离异常并记录 `failures.csv`。
3. **算法模块层**：七个职责单一的处理/评测模块，共用明确的数据契约；模块内部负责色彩空间转换，不把算法状态藏在全局变量中。
4. **数据与评测 I/O 层**：数据预处理、样本清单、GT 掩码读取、指标 CSV 与图表输出。GT 只供离线评测，不能代替运行中的预测掩码。
5. **测试层（横切）**：算法单元测试、输入/GT 配对与掩码 QA、批处理端到端 smoke test。

### 2.2 核心模块与运行顺序

**运行顺序：输入 → M5（可选复原）→ M1（预测肤色掩码）→ M2（曝光）→ M3（空间域平滑）→ M4（频域细节增强）→ M6（白平衡/色彩）→ M7（评价与输出）。**

| 模块 | 责任 | 关键依赖 |
|---|---|---|
| M1 `skin_detect.py` | 从图像预测肤色 mask；提供可视化及对 GT 的 IoU/Precision/Recall 评估 | 输入图像；GT 仅用于离线评估 |
| M2 `exposure.py` | CLAHE 与自适应伽马，尽量限定于肤色区域 | M1 的预测 mask |
| M3 `smooth.py` | 掩码约束的保边平滑、避免损伤五官 | M1 mask；M2 输出 |
| M4 `freq_enhance.py` | 频域低/高频分离、皮肤平滑和细节回注 | M1 mask；M3 输出 |
| M5 `restore.py` | 可选轻微运动模糊复原，置于增强之前 | 输入图；合成模糊参考用于评测 |
| M6 `color.py` | 白平衡与色度约束，减少肤色偏色 | M1 mask；M4 输出 |
| M7 `metrics.py` | 计算指标、汇总 CSV/图表及问卷统计 | 原图、最终/阶段图、预测 mask；相应 GT/参考图 |

M3→M4 是运行时串联关系，二者代码可以并行开发。建议显式区分 `pred_mask` 与 `gt_mask`：预测 mask 参与运行，GT 仅用于离线评测。单张图在流水线中的状态由编排层持有；算法模块间通过显式输入/输出传值，而不直接读写文件系统。配置对象只读传入模块，阶段产物集中由编排层落盘。

### 2.3 建议的接口契约

图像统一为 BGR、`uint8`、`H×W×3`（算法内部可转 float，返回前还原）；掩码统一为同尺寸 `uint8`、前景 255/背景 0，或明确允许 `None`。不得静默混用 BGR/RGB，不得原地修改调用方输入；尺寸不一致应在数据加载处报错，或只对 mask 使用最近邻插值对齐。由于 M1 产生 mask，原有单一 `process(img, mask, cfg) -> img` 不宜强行覆盖检测器：建议 M1 独立提供 `detect_skin(img, cfg) -> pred_mask`；其余图像变换模块使用统一处理接口。若阶段除图像外还要传递 mask 或算法诊断信息，可用轻量 `StageResult(image, artifacts, diagnostics)` 封装；由 `PipelineContext` 保存配置、原图引用及仅评测用的 GT。M7 只读原图、阶段结果、预测 mask 和评测用 GT，不改变图像。先冻结这些数据语义，再决定是否用 dataclass 实现，避免为小型课程项目引入复杂插件框架。

## 3. 开发任务拆分

优先级定义：**P0** 为可运行主链路与必需功能；**P1** 为完整验证、结果整理及课程交付；**P2** 为不阻塞主链路的增强项。人日是工作量估算，不是日历工期。

| ID | 任务与职责范围 / 验收产出 | 优先级 | 工作量 | 建议负责人 | 前置依赖 |
|---|---|---:|---:|---|---|
| T01 | 脚手架、CLI 与配置：建立 `src/beauty/`、目录边界、配置加载/校验、运行命令和环境说明 | P0 | 1.5 人日 | A | 无 |
| T02 | 数据子集与 QA：固定分层样本清单、稳定 seed、配对/缺失检查、图像与 mask 尺寸对齐、协议说明 | P0 | 2 人日 | A | 可与 T01 并行 |
| T03 | 接口与桩测试：冻结图像/mask/GT 语义、`StageResult`（若确有多产物需求）、错误策略；建立可跑单测 | P0 | 1.5 人日 | A | T01；与 T02 并行 |
| T04 | M1 肤色检测与评估：实现传统算法预测 mask、IoU/Precision/Recall、叠加可视化和场景测试 | P0 | 2 人日 | A | T02、T03 |
| T05 | M2 曝光 + M3 空间域平滑：实现 CLAHE/伽马与受 mask 约束的保边平滑、五官保护 | P0 | 3 人日 | A 负责 M2；B 负责 M3 | T03；M2 与 T04 的 mask 接口冻结后集成 |
| T06 | M4 频域增强：低/高频分离、细节回注、频谱图、振铃和尺寸边界测试 | P0 | 2.5 人日 | B | T03；可用桩函数并行，接入依赖 T05/M3 输出约定 |
| T07 | M5 运动模糊复原：确定性基线（合成模糊、已知 PSF、维纳复原）及清晰参考下的 PSNR/SSIM | P0 | 2.5 人日 | C | T03 |
| T08 | M6 白平衡 + M7 评价：肤色色度约束、ΔE/EPI/方差/复原指标与 CSV schema、图表/问卷汇总 | P0 | 4 人日 | C | T02、T03；M7 schema 应尽早与全组冻结 |
| T09 | Pipeline 集成、批处理与端到端测试：依赖顺序、阶段落盘、模块开关、单图错误隔离、坏文件测试 | P0 | 3 人日 | A 主责；B/C 联调 | T04–T08；T02 |
| T10 | 全流程实验与验收：参数版本记录、分层样本检查、生成可复现对比图/结果表 | P1 | 2 人日 | A/B/C | T09 |
| T11 | 个人报告/实验材料与答辩 PPT：基于已验证数据撰写整理，A 负责统稿与叙事一致性 | P1 | 3 人日 | A/B/C | T10 |
| T12 | 演示脚本、问答预案与彩排：现场可运行检查、预设参数、降级演示方案 | P1 | 1 人日 | A 主责，B/C 参与 | T11 |

**基线工作量合计约 28 人日。** 三人并行时，关键路径由接口/数据契约、核心模块集成和后续验收决定，不能简单将总人日除以 3 当作工期。可选 P2：更复杂的自动 PSF 估计、交互式预览界面等，不应阻塞基线流水线；应在 P0 验收后再决定是否投入。

## 4. 依赖顺序与协作方式

```text
T01 ─┐
     ├──> T03 ──> T04(M1) ──> T05(M2/M3) ──> T06(M4) ─┐
T02 ─┘          ├──> T07(M5，可并行) ────────────────────┤
                └──> T08(M6/M7，可并行实现) ─────────────┤
                                                         v
T09(集成) ──> T10(实验验收) ──> T11(报告/PPT) ──> T12(彩排)
```

补充：T05 的 M2 与 M3 可以并行实现，T06 的 M4 可先基于冻结的桩接口开发；图中串行箭头表示运行/集成依赖，不等于必须串行写代码。T08（M6+M7）在 M4/M5 期间可并行开发，但汇总指标的 schema 必须早于联调确定。

- T01 与 T02 可并行；T03 完成接口冻结后，各模块可用桩函数并行开发。M1 验收需等 T02 的 GT；M2/M3/M6 实际接入需等 M1 mask 契约。
- A 负责公共契约、数据/样本准备、M1/M2 与集成；B 负责 M3/M4；C 负责 M5/M6/M7。T08 联调、T09 验收和 T10 文档/答辩共同参与。
- 采用 `feature/<module>-<short-name>` 分支；每个任务提交前跑对应单测，合并前跑全量测试。接口变更先由 A 提 PR/同步讨论，避免模块各自修改契约。
- 每个模块先交可运行基线与测试，再做参数优化；共享固定样本清单、配置版本与 CSV schema。实验结果记录输入样本、配置、代码版本和指标，避免报告数字不可复现。

## 5. 风险与缓解

| 风险 | 影响 | 缓解措施 |
|---|---|---|
| 当前预处理脚本随机抽样，未落实设计文档要求的五类场景各 8 张 | 子集可能缺少遮挡、低曝光或运动模糊样本 | 人工维护带场景标签的 ID 清单并复核；记录 seed、清单和场景覆盖率 |
| 图像为 1024×1024，而合并掩码为 512×512；当前脚本未对齐尺寸 | M1 指标和后续掩码操作错位 | 加载时尺寸断言；统一用最近邻插值对齐 mask；在小样本集上做可视化 QA |
| 文档数据目录命名与实现不一致（如 `skin` 与脚本 `skin_masks`），图像扩展名也有差异 | 集成找不到输入或 GT | 先冻结唯一数据契约，再同步脚本、文档、配置和测试，不靠隐式路径约定 |
| 把 CelebAMask-HQ GT 当作 M1 实际预测 | 不能证明传统肤色检测有效，评估虚高 | 严格分离 `pred_mask`（运行时）和 `gt_mask`（评测时），报告预测性能 |
| 规则肤色检测受肤色、光照、遮挡影响；无条件保留最大连通域也可能误删 | 后续平滑/曝光作用范围错误 | YCbCr/HSV 组合基线，按场景报告指标；最大连通域做可配置选项，并可视化失败例 |
| M5 复原的 PSNR/SSIM 缺少清晰参考图，M3/M4 磨皮也不适合以 PSNR/SSIM 为主 | 结论不严谨 | 仅对合成模糊且保留原清晰图的 M5 实验计算复原指标；磨皮用边缘/纹理/肤色指标和主观评价结合 |
| M4/M5 算法伪影或自动 PSF 估计超出课设时间 | 效果不稳定、进度拖延 | 先完成确定性、可调的基线算法；自动估计列为 P2，记录伪影与运行时间 |
| 单张错误中断批量处理 | 无法稳定产出完整结果 | 逐张 try/except，错误写入 `failures.csv`，整个批次继续；端到端测试覆盖坏文件和缺失文件 |
| A 同时承担架构、数据、M1/M2 和集成，成为瓶颈 | 并行效率下降 | T01 后明确接口与配置，T02 尽早交付；B/C 先用固定样本和桩函数开发，集成按阶段进行 |
