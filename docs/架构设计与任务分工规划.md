## 1. 结论与现状

采用轻量三板块垂直切片，不引入 Web/MVC 或服务化架构。技术栈 Python 3.10.x + OpenCV(headless) + NumPy + Streamlit + scikit-image，全程传统图像处理，禁用深度学习与预训练模型。

仓库当前只有 `src/prepare_data.py`，`beauty` 包、主流程、配置与测试尚未落地。因此本文是开发计划，不代表功能已实现。

## 2. 架构分层（对齐 arch.md 第 4 节）

依赖方向只有一条，不允许反向或跨层：

```text
CLI src/main.py ／ Streamlit src/app.py
              ↓
        core.pipeline + core.config
       ↓            ↓             ↓
  modules M1–M6   metrics M7      io
```

- `main.py` / `app.py` 只调用 `core`，不直接调用任何算法模块。
- `core.pipeline` 是唯一编排点，固定顺序 M5→M1→M2→M3→M4→M6→M7。
- `modules` 之间禁止互相 import；`metrics` 不 import `modules`；算法模块不碰文件系统、UI 与全局状态。
- 磁盘只是持久化边界，不作为模块间通信总线。

## 4. 解耦机制（四条，缺一不可）

1. 依赖倒置：下游依赖冻结契约，不依赖上游实现。M1 未完成时，B/C 用 `prepare_data.py` 生成的 GT 掩码（`skin_masks/`）开发。
2. 文件级私有：一个文件一个 owner，全仓无共享写入文件。
3. 契约即唯一串行点：接口签名、模块配置 schema、掩码与产物落盘规范冻结一次后不得随意变更；变更须开 `change-request` Issue。
4. 集成显式立项：联调是独立 Epic（E4），占排期、有验收标准，不是「做完再说」。

## 5. 跨板块唯一依赖

M6（板块三）需要皮肤掩码做肤色区限定，而掩码由 M1（板块二）产出。这是全局唯一的跨板块数据依赖，靠两条措施解耦：掩码格式在 E0 冻结为 `uint8 H×W`、取值 `0/255`，M6 只依赖格式、不 import `skin_detect.py`；M1 未完成期间 C 使用 GT 掩码开发，`core.pipeline` 传入的掩码来源对 M6 不可见。

## 8. 分支与协作规范

- 每人一条长期分支，命名用自己的名称简称：A（`guts-yang`）用 `lcy`，B（`qixing1227`）用 `qx`，C 用自己的简称。
- 流程：`git checkout main` → `git pull` → `git checkout -b <简称>` → 在自己分支开发 → `git push -u origin <简称>` → 发 PR 到 `main`。
- PR 描述写 `Closes #xx` 关联 Issue；由 A（GitHub `guts-yang`）统一 review 合并；必须通过 CI。
- 模块 PR 只能改本模块、本模块 YAML 与测试，不得夹带 `core/`、`io/`、`pipeline.yaml`、CI 改动。
- 接口或契约变更先提 `change-request` Issue 评审，不得私自改签名。
