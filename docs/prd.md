## 1. 用途与范围

本文件规定需求的编写方式、字段、优先级、验收格式及项目需求清单。它描述“系统要做什么”，不替代 [design.md](./design.md) 的设计约束，也不替代 [arch.md](./arch.md) 的架构约束。

本项目范围分为两类：

- 软件范围：M1–M7、单图/批量命令行流程、本地 Streamlit 演示、配置、评价与测试。
- 课程交付范围：个人课程设计报告、课程实验报告、答辩材料及可运行程序；这些属于交付物，不都属于软件功能。

## 2. 需求编写模板

每条需求必须包含需求标题/陈述及以下四个强制字段，缺一不可：

| 字段 | 规则 | 格式 |
| --- | --- | --- |
| 编号 | 唯一且不可复用；须可追溯到课程要求或新增目标 | `R<n>` 或 `R<n>.<m>` |
| 优先级 | 交付重要度 | `P0` / `P1` / `P2` |
| 验收标准 | 可重复判定的通过条件 | 量化指标协议或 Given-When-Then（GWT） |
| 负责人 | 唯一最终负责人与验收答复人 | `A` / `B` / `C` |

“协作者”“来源”“依赖”“备注”是可选补充字段，但不能替代唯一负责人。多人参与时，指定一名最终负责人，其余列为协作者；若成果可独立验收，则拆成多个需求。

## 3. 编号、优先级与验收规则

### 3.1 编号与课程追溯

- `R1`–`R7` 严格沿用课程题目 4 的列举顺序，**不代表 M1–M7 模块序号**。
- 子项使用 `R<n>.<m>`，必须能够单独测试或验收。
- `R8` 起用于项目运行、配置、交互和增强需求。
- 已分配编号不得重用；需求撤销时保留编号并标记“已撤销”。

| 需求编号 | 课程要求 | 实现模块 |
| --- | --- | --- |
| R1 | 色彩空间转换与肤色区域检测 | M1 肤色检测 |
| R2 | 空间域滤波平滑皮肤并保护边缘 | M3 空间域平滑 |
| R3 | 频率域低通/高通组合磨皮与细节增强 | M4 频域增强 |
| R4 | 直方图均衡或伽马校正改善曝光 | M2 曝光改善 |
| R5 | 轻微运动模糊复原 | M5 图像复原 |
| R6 | 彩色增强与白平衡 | M6 色彩处理 |
| R7 | 主观评价为主，辅以边缘保持指标 | M7 评价 |

### 3.2 优先级定义

| 等级 | 含义 | 裁剪规则 |
| --- | --- | --- |
| P0 | 课程必需能力或最小可运行闭环；缺失即不能视为满足课程题目 | 最终课程交付不得裁剪 |
| P1 | 提升可用性、演示或工程体验，但不是课程题目中的独立算法要求 | 工期不足时须评估影响并经组内确认 |
| P2 | 可选增强 | 可在不影响 P0/P1 验收的前提下裁剪 |

优先级用于确定交付范围，不规定开发顺序。测试、评审和质量门禁须与功能开发并行，不得等所有 P0 完成后才开始。下表分级是项目草案，不代表课程官方分级。

### 3.3 验收标准格式

- 模块能力优先采用“量化指标 + 测试条件”。
- 流程与交互采用 GWT：Given（前置条件/输入）、When（操作）、Then（可观察结果、错误处理及必要时限）。
- 视觉检查可作为补充，但须引用固定样例、检查清单、检查人数与记录方式；不得只写“效果好”“无明显伪影”“实时”等不可判定措辞。
- 未通过试测和评审的数值均标记为**候选阈值**，在基线确认前不得当作已冻结验收线。

### 3.4 指标测量协议（候选）

共同约定：图像使用 8-bit；评测样本及场景标签以 `assets/evaluation_manifest.csv` 为唯一固定清单；GT 标签图用最近邻插值对齐到输入图尺寸；所有指标逐图计算，再报告宏平均、中位数和有效样本数。除特别说明外，皮肤 GT 腐蚀使用 `11×11` 椭圆结构元素（半径 5 px），图像滤波边界使用 `BORDER_REFLECT_101`。随机退化须记录随机种子及参数。无有效 GT、空区域或参考图的指标标记为不可评估并说明原因，不得填 0 冒充有效结果。

课程算法阈值采用固定样本上的**模块隔离评测**：每次只运行被测模块，避免前序模块改变输入；M2/M3/M4/M6 的隔离评测使用皮肤 GT 掩码，M1 单独评测预测掩码，M5 使用由清晰参考合成的模糊输入。端到端运行另行报告，不替代模块隔离验收。正式评测配置须记录 profile、被测模块、掩码来源和有效参数。

| 指标 | 计算协议 |
| --- | --- |
| 肤色 IoU / Recall | 二值化后按 `IoU=TP/(TP+FP+FN)`、`Recall=TP/(TP+FN)` 逐图计算，再宏平均。以 CelebAMask-HQ 皮肤 GT 为准；GT 为空的样本单独报告、不参与均值。 |
| 皮肤局部方差下降率 | BGR 转 YCrCb 后取 8-bit Y；用 7×7 滑动窗口按 `Var=E(Y²)−E(Y)²` 计算方差图，仅对皮肤 GT 腐蚀 5 px 后的窗口中心像素取均值；`V_before`/`V_after` 分别为被测阶段输入/输出的区域方差均值；逐图计算 `D=(V_before−V_after)/max(V_before, ε)` 后宏平均，`ε=1e-6`；若 `V_before<ε`，标记不可评估。 |
| 项目自定义 EPI | BGR 转 YCrCb 后取 8-bit Y，以 `CV_32F`、Sobel `ksize=3`、`BORDER_REFLECT_101` 计算梯度幅值；在 `face_feature_gt` 区域比较阶段输入/输出梯度，逐图计算 `EPI=Σmin(g_before,g_after)/(Σmax(g_before,g_after)+ε)`，范围 0–1，`ε=1e-8`；区域为空或分母过小时标记不可评估。五官标签集合在评测协议中固定。 |
| 高频能量保留率 | 在皮肤 GT 腐蚀 5 px 区域，对 Y 通道定义 `HP(Y)=Y−GaussianBlur(Y,ksize=0,sigmaX=3.0,sigmaY=3.0,borderType=BORDER_REFLECT_101)`，计算 `R_HF=RMS(HP(after))/max(RMS(HP(before)), ε)`；报告逐图值和宏平均。σ=3.0 为候选测量参数，基线确认前试测。 |
| 曝光改善 | 使用 YCrCb 的 8-bit Y。欠曝候选样本定义为阶段输入皮肤 GT 平均 Y < 90；亮度相对变化为 `(mean_after−mean_before)/max(mean_before,1)`；过曝比例为阶段输出皮肤 GT 中 `Y>250` 的像素占比。亮度和过曝统计使用同一张图、同一皮肤 GT 区域。阈值须试测。 |
| 运动模糊复原 | 从清晰参考图用固定并记录的线性运动 PSF 合成模糊输入；分别计算模糊输入和 M5 输出相对清晰参考的 PSNR/SSIM。输入先由 BGR 转 RGB；PSNR 使用 `data_range=255`，SSIM 使用 `channel_axis=-1`、`data_range=255`、`win_size=7`。PSF、噪声和随机种子写入评测协议。 |
| 肤色 ΔE2000 | 对清晰参考图施加评测配置中固定的合成 RGB 通道增益偏色，再将校正结果与原清晰参考比较；BGR 转 RGB 后按标准 sRGB/D65 转 Lab 并计算 CIEDE2000，在皮肤 GT 内逐像素计算、逐图取平均，再对图像宏平均。增益向量须记录；无可信参考图时标记不可评估。 |

评测集候选规模为 40 张。当前数据预处理脚本按随机种子抽取，但没有场景分层，也没有输出固定样本清单；因此必须生成并审阅带相对路径和场景标签的 `manifest.csv`，不能仅凭随机种子宣称实现了“五类场景各 8 张”。

### 4.4 工程质量门禁（独立于需求优先级）

- 单元测试由模块负责人维护：A 负责 M1/M2，B 负责 M3/M4，C 负责 M5/M6/M7；A 维护 CI 与主流程集成测试。
- 每个模块至少有正向、边界、输入不变性和输出格式/尺寸契约用例。
- PR CI 只使用内存生成的合成图像、掩码和小型 CSV fixture；不得依赖未入库的 CelebAMask-HQ 或开发者本机文件。
- 真实数据集测试标记为 `integration`，本地下载数据后单独运行。
- 所有功能 PR 均须通过 CI；优先级不能豁免测试门禁。

## 5. 范围边界与课程交付物

### 5.1 软件范围

- M1–M7、单图 CLI、目录批处理、本地 Streamlit 演示、模块参数配置。
- CLI `process` 运行可产出最终图、可选阶段图和失败清单；`evaluation` 运行使用固定 manifest/GT，额外产出指标 CSV 与必要图表。Streamlit preview 默认仅在本地内存处理，用户显式导出时才保存图像结果。
- pytest 单元/契约测试及需要本地数据的集成评测。

### 5.2 不在软件范围

- 深度学习、预训练人脸模型、人脸身份识别或属性分类。
- 移动端 App、账号系统、云端服务、多人并发与高可用部署。
- 未列入题目 4 且未通过 `change-request` 评审的算法功能。

## 7. 变更控制

1. 基线确认后新增、删除需求或改变验收条件，必须创建 GitHub Issue 并加 `change-request` 标签。
2. 变更 Issue 写明理由、受影响需求/模块、依赖、工期影响和回归测试范围。
3. A 组织评审；三人同意后修改本 PRD，并同步更新 design.md、arch.md、相关 Issue 与测试协议。
4. 未经评审的口头变更不得作为验收依据。
